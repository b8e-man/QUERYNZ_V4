A register behind a portal search that answers every match on one page is enumerated by its own drop-down lists, never by an empty search: the empty one is the heaviest request a host can be asked.
area: capture, registers, politeness, building_practitioners

Why: the building practitioners register (`kete-lbp.mbie.govt.nz`, a Power Apps portal) returns every match of a GET search in one table with no paging. A search with no criterion did not answer in 60 s on 2 November 2026; the seven licence-class searches answered, the largest (Carpentry, 21,372 rows, 18 MB) in seconds. The 7 classes and 19 areas of practice together list 42,091 rows, the union is the current register. Two more traps the same page set: the box "include not currently licensed" changes nothing on a class search (lapsed practitioners hold no class), and the practitioner's page loads its sub-tables by a POST the fetch gate does not make, so a reader sees only the page's own fields. Measure the page's printed fields before reading: this one prints a postcode, an email address and four telephone fields beside the name, and the reader names the fields it keeps rather than skipping the ones it knows.
