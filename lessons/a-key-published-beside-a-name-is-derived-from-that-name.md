Why: the site published `pub.names.name_key` as a donor's `name_key`. The links had read one Part A row before party-returns-5 fixed its name cell, so the key carried a residence after the name while the display name was clean; and rows loaded after the links ran had no key at all, so the site keyed them apart and wrote a second page for 54 donors. Both faults were the same thing: a field the site did not derive and could not check.

How to apply: a published key is a function of the published display name (`paths.name_key`), so a reader can match it by eye and a gate can check it (`name-keys`: every key's words are in the name beside it; no name field or path carries a residence word). A reading from another module may fold rows inside the build and never be a field. When a row has no reading yet, fold it by its exact filed spelling and say so in the basis; do not key it apart.
