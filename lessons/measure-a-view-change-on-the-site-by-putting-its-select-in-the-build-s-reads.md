Measure a view change against the frozen site by building it in scratch with the read login and the view's new SELECT put in place of its name; a session may not write a view on live.
area: published views, site build, comparison, measurement, scratch

Why: candidate-returns-3 changed `pub.candidate_return_totals` (a UNION with the Commission's rows) and had to count how many comparison differences fell. `support.db.guard` refuses the owner login on `querynz_v4` to an unmarked session, and the sample database is for building, never for measuring. Wrapping `read.product_connect` so `execute` replaced `pub.candidate_return_totals` with `(<the view's SELECT>) AS candidate_return_totals` over the live lane tables, and building twice from the same frozen listing (base unpatched, branch patched), gave a like-for-like count: the base reproduced the day file's 5,133 exactly, which is what made the branch's figure trustworthy. A column the branch adds and the live table lacks yet is stood in by a CTE in the substituted SELECT.

How to apply: build base and branch from the same listing in the same run, check the base reproduces the frozen day's figure for the cause, then report the branch's; compare the whole cause table, not just the cause, because differences move between causes (here `cite-key` +675, one per new row, and `nil-return-is-a-zero` +740). The script is `scratch/candidate-returns-3/measure.py`.
